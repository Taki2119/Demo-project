# Data schema — SaaS Analytics Demo

> The source of truth for the schema is `supabase/migrations/*.sql`. This file explains WHY and
> how to read the numbers. Change the schema ⇒ update both, and run `npm run db:test`.

All data is **synthetic data** generated by a script: company names, person names, emails and
plan names are all fictional. There is no real data from any organization.

## 1. Foundational decisions

| Decision | Choice | Notes |
|---|---|---|
| Database | **Supabase (Postgres)** instead of BigQuery | Knock-on changes: see §7 |
| Business time zone | `Asia/Ho_Chi_Minh` | Every `date` column is a date in this time zone. Can be changed, but the data must be regenerated |
| Currency | **Japanese yen `JPY`**, type `numeric(14,0)` | Integers, no fractional part. One dataset = one currency, no conversion in the DB |
| Language | DB: column names + value codes in **English** · display: **ja / vi** | Labels in `mart.column_labels` + `mart.labels` (§4.3) |
| "Today" | `raw.dataset_meta.as_of_date` | Static data stays consistent no matter which day it is opened |
| Time ranges | Half-open `[valid_from, valid_to)` | `valid_to` = the FIRST day no longer in effect; `null` = still in effect |
| Month | `date` on day 1 (`2026-04-01`) | The API returns `YYYY-MM`; the client never goes through `new Date(str)` |

## 2. Two layers

```
raw.*   (generated "business" data)  ──refresh──▶  mart.*   (the ONLY thing the app + AI read)
```

- `raw` and `mart` are **not exposed via Supabase's REST API** (only `public` is exposed). The client
  never reads the DB directly; the read path is Vercel using the `analytics_reader` role.
- `mart` consists of plain views + 3 materialized views (`company_mrr_monthly`, `user_monthly`,
  `churn_risk_snapshot`). After every data load: `select mart.refresh();`.

## 3. RAW layer

| Table | One row is | Key | Notes |
|---|---|---|---|
| `dataset_meta` | one attribute of the generation run | `key` | `as_of_date`, `seed`, `generated_at` |
| `plans` | one plan | `plan_id` | `tier` 1→3 to classify upgrades/downgrades |
| `features` | one feature | `feature_id` | `is_key` = retention feature, used as a risk signal |
| `staff` | one sales/CS staff member | `staff_id` | receives the care list |
| `companies` | one customer company | `company_id` | ⚠ `name` is NOT unique, do not use it as a key |
| `users` | one user (seat) | `user_id` | `deactivated_at` = first day no longer a seat |
| `subscriptions` | one subscription lifecycle | `subscription_id` | Churn then come back = a NEW subscription |
| `subscription_periods` | one segment (plan, seats, MRR) | `(subscription_id, valid_from)` | **Source of truth for MRR.** Trial = row with `mrr = 0` |
| `cancel_requests` | one **cancel scheduled** request | `request_id` | `withdrawn_at` ⇒ customer was retained |
| `invoices` | one monthly invoice | `invoice_id` | `plan_id` = the plan billed |
| `user_activity_daily` | day × user who used it | `(activity_date, user_id)` | **SPARSE table:** no row = no usage (a true 0) |
| `feature_usage_daily` | day × company × feature | `(activity_date, company_id, feature_id)` | Sparse table, as above |
| `interventions` | one care action | `intervention_id` | The project page measures effectiveness with this table |

Invariants that cannot be declared as constraints live in `mart.dq_checks` (one row per rule,
`failed_rows` must be 0): segments of a subscription do not overlap · the last segment ends
exactly on the churn date · activity falls within the user's lifecycle and the right company ·
**MRR identity** (§4.1).

## 4. MART layer — how to read the numbers

**Rule 1: the mart carries only ADDITIVE numbers.** Ratios (ARPA, churn rate, stickiness, seat
utilization…) are computed on the client from the totals. Reason: "all plans" = sum of the plans, and
summing ratios is wrong; a ratio column in the mart will sooner or later get summed by someone.

**Rule 2: (month × plan) tables are DENSE.** A month with nothing still has a row with true 0s, so
the client does not have to LOCF. Each company is in exactly one plan in a month ⇒ summing the plans
gives the correct total, even for stock numbers.

**Rule 3: the running month is PROVISIONAL.** Stock state is measured at `measure_date` = end of
month, or `as_of` for the running month. `is_closed = false` ⇒ do not compare periods with this month
as if it were a full month.

| View | Grain | Used for |
|---|---|---|
| `months` | month | time axis, `measure_date`, `is_closed` |
| `company_mrr_monthly` | month × company | MRR, plan, movement type of each company |
| `mrr_movements` | month × company × plan × type | MRR movements, with plan changes split out |
| `revenue_monthly` | month × plan (dense) | **Revenue** board |
| `user_monthly` | month × user | **By user** board |
| `users_monthly` | month × plan (dense) | **User count** board |
| `company_monthly` | month × company | **By company** board |
| `churn_risk_snapshot` | Sunday × paying company | risk score history (52 weeks) |
| `churn_watchlist` | company (latest snapshot) | **churn prevention project** page |
| `interventions_monthly` | month × trigger source × channel | care effectiveness |
| `plans` / `features` / `staff` | catalogs | labels, filters |
| `dq_checks` | rule | checks after every load |

### 4.1 MRR movement classification

Compare the company's MRR this month with last month:

| Type | Condition | `mrr_delta` |
|---|---|---|
| `new` | before = 0, now > 0, **never** paid before | + now |
| `reactivation` | before = 0, now > 0, has paid before | + now |
| `expansion` / `contraction` | same plan, MRR up / down | now − before |
| `churn` | before > 0, now = 0 (attributed to last month's plan) | − before |
| `plan_out` + `plan_in` | **plan change**: one row in the old plan, one row in the new plan | − before / + now |

Plan changes are split into two rows so that the following identity holds for **each plan**, not only
for the total:

```
mrr_end(month) − mrr_end(previous month) = new + reactivation + expansion + contraction + churn + plan_in + plan_out
```

If a plan change were folded into the new plan's `expansion`, the old plan would lose MRR with no
movement explaining it. `dq_checks.mrr_identity_per_plan` locks this identity.

### 4.2 Formulas computed on the client (from mart columns)

| Metric | Formula | Notes |
|---|---|---|
| ARPA | `mrr_end ÷ paying_companies` | `null` when the denominator = 0 |
| Gross MRR churn | `−(churned_mrr + contraction_mrr) ÷ mrr_end of the PREVIOUS month` | The denominator is the START of the period |
| Net revenue retention | `(previous month's mrr_end + expansion + contraction + churn + plan_in + plan_out) ÷ previous month's mrr_end` | Existing customers only: excludes new, reactivation. Meaningful at the ALL PLANS level (per plan, a plan change makes the customer "leave" that plan) |
| Logo churn | `churned_companies ÷ previous month's paying_companies` | |
| Average DAU | `active_user_days ÷ days_in_period` | |
| Stickiness | `average DAU ÷ mau` | |
| Seat utilization | `mau ÷ seat_users_end` | |
| Collection rate | `paid_amount ÷ invoiced_amount` | |

### 4.3 ja / vi labels

The DB keeps column names and value codes in English, because they are stable and easy to write SQL
against. What users **see** comes from two tables in `mart`, shared by both the web app and the AI:

| Table | Key | Carries |
|---|---|---|
| `column_labels` | `column_name` | `ja`, `vi`, `unit` (`JPY` · `人` · `社` · `日` · `%`…). Same column name = same meaning in every view |
| `labels` | `(domain, code)` | `ja`, `vi`, `sort_order`, for the domains `plan` · `feature` · `industry` · `region` · `size_band` · `acquisition_channel` · `team` · `user_role` · `cancel_reason` · `invoice_status` · `movement` · `plan_change` · `risk_band` · `top_reason` · `intervention_*` · `metric` (names of metrics computed on the client) |

- **UI** text (buttons, filters, messages, the language switch) is NOT here: it belongs to the
  frontend's i18n dictionary.
- Proper names (companies, people) have only one form and are not translated.
- Add a new column or code and forget the label ⇒ tests go red: `generate.test.mjs` checks EVERY
  column of the views in `mart` and EVERY code that appears in the data.

## 5. Churn risk score (v2)

Every Sunday, for every **paying** company. Compare the last 28 days with the 28 days before:

| Component | Points |
|---|---|
| **Usage:** nobody logged in for > 14 days, or user-days down ≥ 50% / ≥ 30% / ≥ 15% | 40 / 40 / 25 / 10 |
| **Seats:** WAU (users active in 7 days) ÷ seats < 20% / < 40% | 20 / 10 |
| **Key features:** dropped entirely or down ≥ 50% / down ≥ 25% / never used | 30 / 15 / 10 |
| **Billing:** has an overdue invoice | 10 |

⚠ Version v1 measured *"days with nobody logged in"* and *"users active within 28 days"*, and almost
never raised an alarm: companies with many users rarely have 7 blank days. On the test data, v1 put
most about-to-churn companies in the `low` band. Version v2 measures **trends**:

| Band | Churn rate within 90 days (test data) |
|---|---|
| `low` | 1.4% |
| `medium` | 8.2% |
| `high` + `cancel_scheduled` | 44.1% |

- `risk_score` = sum, capped at 100. Band: **≥ 60 `high`** · **≥ 30 `medium`** · otherwise `low`.
- **Open cancel scheduled request** ⇒ band `cancel_scheduled`, ranked above any score: the customer
  has said they want to leave.
- `top_reason` = the heaviest-scoring component, used to suggest how to care for the customer.
- `churned_within_90d` is the **label** used to measure whether the score is right: did the company
  churn within 90 days after the snapshot date. `null` when 90 days have not yet passed.
  ⇒ The project page can report *"of the `high` companies 3 months ago, what % have churned"*.
- The thresholds are **heuristics**. Change them in the migration, then review the table above: the
  test prints it on every run, and blocks when the risky band does not churn at least 3× more than
  the low band.

## 6. Permissions

- Role **`analytics_reader`**: only `SELECT` on `mart`. Every transaction is READ ONLY by default,
  `statement_timeout = 15s`. So SQL written by the AI, even if wrong, can neither write nor hang
  the DB. The guardrail is Postgres permissions, not a regex in code.
- `mart.as_of()` is `SECURITY DEFINER`. Functions called inside a view run with the **caller's**
  privileges, so without this flag `analytics_reader` fails right at `mart.months`.
- RLS is enabled on every `raw` table (with no policies); `anon` / `authenticated` have their
  privileges revoked on both schemas.

**One-time manual step on Supabase** (the password is NOT in the repo):

```sql
alter role analytics_reader with login password '<strong password>';
```

The connection string for Vercel uses the pooler (Supavisor, transaction mode, port 6543), with a
user of the form `analytics_reader.<project-ref>`. Store it only in Vercel's environment variables.

## 7. Supabase instead of BigQuery: what changes

| Part | Original (BigQuery) | This version (Supabase) |
|---|---|---|
| Aggregation layer | scheduled query | view + materialized view, `mart.refresh()` (can be run with `pg_cron`) |
| Board read endpoint | `board-data`: service account → `jobs.query` | `board-data`: role `analytics_reader` → `select * from mart.<view>` |
| AI SQL tool | dry-run + regex allowing only `SELECT` | READ ONLY transaction + schema permissions; `EXPLAIN` first to block overly heavy queries |
| Size limit | 4.5 MB / CSV | still keep a cap per response; filter by time range in SQL |

## 8. Data generator — `scripts/data/`

```bash
npm run data:generate            # → data/out/*.csv (one file per raw table; data/ is not in git)
npm run data:load                # wipe raw then COPY again, mart.refresh(), print dq_checks
```

- Parameters: `-- --seed <string> --as-of YYYY-MM-DD --months <n> --arrivals <new companies/month>`.
  Defaults: `demo-2026` · `2026-11-10` · `24` · `8`.
- `data:load` reads `DATABASE_URL` from `.env` (already in `.gitignore`). Use the **Session
  pooler** string (port 5432, user `postgres.<project-ref>`) from *Supabase → Connect*. Do not use
  `analytics_reader`, because that role is read-only. The raw part runs in ONE transaction: if it
  fails midway, the DB keeps the old set.
- **Pure, seeded functions:** same parameters ⇒ byte-identical CSV (locked by tests). There is no
  `Math.random()`; each company has its own PRNG branch, so tweaking one company does not shift the
  others.

| `users` | 5,103 |
| `subscriptions` | 263 |

  within the free plan's 500 MB cap.

**The simulated story** (details at the top of `generate.mjs`):

| Component | Simulation |
|---|---|
| New companies | Arrive monthly, growing about 3%/month. Japanese-style seasonality: April high, December and March low |
| Health | Each company has a **hidden health** that drifts month to month. It drives usage, seat growth / plan upgrades, late payment, and churn risk (about 1.6%/month when healthy, about 6% when weak) |
| Before churn | **Usage declines over 35–90 days** (key features drop faster than logins). About 65% schedule a cancellation 10–35 days ahead. About 55% receive care, and about 30% of those are retained (cancel scheduled request withdrawn) |
| Noise | Healthy companies also have short dips; long holidays (New Year, Golden Week, Obon) dent activity; 12% of users are "ghost seats" that are bought but almost never log in |
| Trial | 14 days, for the self-signup and inbound channels. Conversion to paid depends on health |
| Return | 15% of churned customers come back after 2–8 months |
| Future | No date after `as_of`. A cancellation scheduled after `as_of` ⇒ the subscription is still active, with only an open cancel scheduled request |

**Person and company name data:**
- Company and person names are **random combinations** of fragments in `names.mjs` (common family
  names, given names, made-up compound words + industry suffixes). Not taken from any list of real
  companies or people.
- Emails are always in the `*.example.com` domain (RFC 2606), so they cannot point to anyone real.

**Pricing (JPY, integers):** `MRR = base fee + max(0, seats − included seats) × seat price`,
customers via partners get a 10% discount.

| Plan | Base fee | Included seats | Extra seat price |
|---|---|---|---|
| Starter | ¥9,800 | 3 | ¥1,200 |
| Growth | ¥29,800 | 10 | ¥1,800 |
| Scale | ¥98,000 | 30 | ¥2,400 |

## 9. Testing — `npm run db:test`

Runs on **PGlite** (Postgres compiled to WASM, no server to install). Run measured 2026-11-11:
16 tests green, about 90 seconds.

**`schema.test.mjs`** uses a 3-company scenario with hand-computed answers: upgrade, downgrade,
churn, return, cancel scheduled, deactivated user, stopped usage. It locks:
- the numbers of `revenue_monthly` and `users_monthly`;
- the risk score;
- the permissions of `analytics_reader`.

**`generate.test.mjs`** generates data (18 months), COPYs it into the DB, then checks:
- `dq_checks` = 0;
- no date after `as_of`;
- byte-for-byte reproducibility;
- money is integer yen;
- every column and every value code has ja/vi labels;
- the churn signal is real (table in §5).
